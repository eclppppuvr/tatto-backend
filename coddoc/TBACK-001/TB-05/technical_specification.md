## 1. Обзор изменения

### 1.1. Что делаем и тип изменения
**Суть:** Пользователь выбирает существующий эскиз (извлечённый или сгенерированный) и предустановленный манекен (рука, нога, спина, грудь и т.д.). Система асинхронно накладывает эскиз на выбранную часть тела с учётом анатомических изгибов через AI-пайплайн (stub на MVP). Результат — реалистичная визуализация будущей татуировки в MongoDB. Пользователь видит прогресс через WebSocket с fallback на polling.

**Тип:** новый функционал
**Стороны:** Fullstack

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| API (tatto-backend) | Новый сервис, владелец всех взаимодействий | Команда проекта | 🟢 |
| Celery worker | Асинхронная обработка AI-пайплайна | Команда проекта | 🟢 |
| S3 (MinIO) | Хранение результирующих изображений | Команда проекта | 🟢 |
| PostgreSQL | Хранение Jobs (статус, прогресс) | Команда проекта | 🟢 |
| MongoDB | Хранение примерок (tryons) | Команда проекта | 🟢 |
| Redis | Broker для Celery, pub/sub для WebSocket | Команда проекта | 🟢 |

### 1.3. Связь с бизнес-требованиями
Реализует FR-3 из БТ: пользователь выбирает эскиз и манекен, получает реалистичную визуализацию татуировки на теле.

## 2. Взаимодействия (ядро)

### INT-1. Отправка запроса на примерку — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** пользователь нажимает «Примерить» на экране результата эскиза
- **Контракт (запрос):** `POST /v1/tryon`
  - Authorization: `Bearer <access_token>`
  - `sketch_id` (string, required) — MongoDB _id эскиза (из TB-03 или TB-04)
  - `body_part` (enum, required) — часть тела: `arm`, `leg`, `back`, `chest`, `shoulder`, `calf`, `wrist`, `neck`
  - `params` (object, optional) — параметры позиционирования:
    - `scale` (float, 0.1–5.0, default 1.0) — масштаб
    - `rotation` (float, -180–180, default 0) — поворот в градусах
    - `opacity` (float, 0.0–1.0, default 1.0) — прозрачность
    - `offset_x` (float, -100–100, default 0) — смещение по X
    - `offset_y` (float, -100–100, default 0) — смещение по Y
- **Контракт (ответ):** `202 Accepted`
  - `job_id` (UUID) — ID задачи
  - `status` (enum: `pending`) — начальный статус
- **Пример запроса:**
  ```json
  {
    "sketch_id": "sk_a1b2c3d4e5f6",
    "body_part": "arm",
    "params": {
      "scale": 1.2,
      "rotation": 15,
      "opacity": 0.9,
      "offset_x": 10,
      "offset_y": -5
    }
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "job_id": "j1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "status": "pending"
  }
  ```
- **Ошибки:**
  - `400 Bad Request` — «sketch_id обязателен» / «body_part не в enum'е»
  - `404 Not Found` — «Эскиз не найден»
  - `403 Forbidden` — «Эскиз не принадлежит пользователю»
  - `422 Unprocessable` — «params.scale вне диапазона 0.1–5.0»
  - `401 Unauthorized` — «Неавторизован»
- **Состояния UI по ответу:** значение → показать job_id, переключиться на экран прогресса; ошибка → показать сообщение
- **Авторизация:** JWT required
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### INT-2. Получение статуса Job — 🟢
- **Вид:** новое (дублирует INT-2 из TB-03, TB-04, но для try_on type)
- **Граница/направление:** FE → BE
- **Триггер:** polling (каждые 5 сек) или WebSocket disconnect
- **Контракт (запрос):** `GET /v1/jobs/{job_id}`
  - Authorization: `Bearer <access_token>`
- **Контракт (ответ):** `200 OK`
  - `id` (UUID)
  - `status` (enum: `pending`, `running`, `done`, `failed`, `cancelled`)
  - `progress` (integer, 0–100) — текущий прогресс
  - `output_ref` (string | null) — S3-ключ или MongoDB _id результата
  - `error_code` (string | null) — машинный код ошибки
  - `error_message` (string | null) — человекочитаемое описание ошибки
  - `created_at` (ISO 8601)
  - `finished_at` (ISO 8601 | null)
- **Пример ответа (done):**
  ```json
  {
    "id": "j1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "status": "done",
    "progress": 100,
    "output_ref": "ty_a1b2c3d4e5f6",
    "error_code": null,
    "error_message": null,
    "created_at": "2026-10-31T10:00:00Z",
    "finished_at": "2026-10-31T10:01:15Z"
  }
  ```
- **Ошибки:**
  - `401 Unauthorized` — «Токен недействителен»
  - `403 Forbidden` — «Job не принадлежит пользователю»
  - `404 Not Found` — «Job не найден»
- **Состояния UI по ответу:** `pending` → спиннер; `running` → прогресс-бар; `done` → показать результат; `failed` → показать ошибку + кнопку «Повторить»
- **Авторизация:** JWT required
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-3

### INT-3. WebSocket: получение прогресса — 🟢
- **Вид:** новое (дублирует INT-3 из TB-03, TB-04)

- **Триггер:** подключение клиента к WebSocket-каналу
- **Контракт (подключение):** `WS /v1/ws/jobs/{job_id}`

- **Контракт (сообщение от сервера):** JSON

  - `job_id` (UUID)
  - `progress` (integer, 0–100)
  - `status` (enum: `pending`, `running`, `done`, `failed`)
  - `message` (string | null)
- **Пример сообщения (done):**
  ```json
  {
    "type": "done",
    "job_id": "j1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "progress": 100,
    "status": "done",
    "message": null
  }
  ```
- **Ошибки подключения:**
  - `401 Unauthorized` — токен недействителен
  - `404 Not Found` — job не найден
- **Состояния UI по ответу:** `progress` → обновить прогресс-бар; `done` → показать результат; `error` → показать ошибку
- **Авторизация:** JWT в query-параметре

## 3. Backend — ответственность

### 3.1. По сервисам

**API (tatto-backend)** — реализует INT-1, INT-2, INT-4, INT-5.

- INT-1 (tryon request): валидация sketch_id и body_part, проверка ownership эскиза (sketch_id принадлежит user_id из JWT), создание Job в PostgreSQL со статусом `pending`, публикация события в Redis для Celery, возврат `job_id`
- INT-2 (job status): чтение Job из PostgreSQL, проверка ownership
- INT-4 (tryon detail): чтение примерки из MongoDB, проверка ownership
- INT-5 (tryons history): чтение примерок из MongoDB, пагинация

**Celery worker** — обработка AI-пайплайна.

- Подписка на очередь `gpu` (Celery + Redis broker) — try-on требует больше ресурсов
- Забирает задачу из очереди, обновляет Job на `running`, публикует прогресс в Redis pub/sub
- Вызывает AIEngine.try_on() (stub на MVP)
- Сохраняет результат в S3 (`tryons/{uuid}.png`), создаёт документ в MongoDB (tryons)
- Обновляет Job на `done` (или `failed` при ошибке)

**S3 (MinIO)** — хранение изображений.

- Bucket `tattoo`, префикс `tryons/`
- Ключи иммутабельны

**PostgreSQL** — хранение Jobs.

- Таблица `jobs`: type=`try_on` (ENUM), статусы и прогресс как в TB-03

**MongoDB** — хранение примерок.

- Коллекция `tryons`: `_id` (ObjectId, PK), `user_id` (UUID), `sketch_id` (ObjectId, FK → sketches._id), `body_part` (ENUM: `arm`, `leg`, `back`, `chest`, `shoulder`, `calf`, `wrist`, `neck`), `params` (object: `scale`, `rotation`, `opacity`, `offset_x`, `offset_y`), `status` (ENUM: `active`, `deleted`, default `active`), `s3` (object: `result_png`, `mask_png`, `thumbnail`), `meta` (object: `model`, `pose_confidence`, `latency_ms`), `created_at` (ISODate)

**Redis** — broker + pub/sub.

- Broker для Celery: `redis://:password@localhost:6379/0`
- Pub/sub каналы: `job:channel:{job_id}`

### 3.2. Данные и хранение

- 🟢 `jobs` (PostgreSQL) — таблица: `type` (ENUM: `extract_sketch`, `generate_design`, `try_on`), для try-on: `input_ref` = sketch_id + body_part + params (TEXT), `output_ref` = MongoDB _id
- 🟢 `tryons` (MongoDB) — коллекция: `_id` (ObjectId, PK), `user_id` (UUID), `sketch_id` (ObjectId, FK → sketches._id), `body_part` (ENUM: `arm`, `leg`, `back`, `chest`, `shoulder`, `calf`, `wrist`, `neck`), `params` (object: `scale` float, `rotation` float, `opacity` float, `offset_x` float, `offset_y` float), `status` (ENUM: `active`, `deleted`), `s3` (object: `result_png` string, `mask_png` string, `thumbnail` string), `meta` (object: `model` string, `pose_confidence` float, `latency_ms` int), `created_at` (ISODate)
- Индексы MongoDB: `{user_id: 1, created_at: -1}`, `{sketch_id: 1}`
- Миграции: нет (таблицы создаются в TB-03)

### 3.3. Авторизация/доступ на бэке

- INT-1, INT-2, INT-4, INT-5 требуют JWT в заголовке `Authorization: Bearer <token>`
- Валидация: проверка подписи JWT, срока действия
- INT-1: проверка ownership эскиза (sketch_id принадлежит user_id из JWT)
- INT-2, INT-4, INT-5: проверка ownership (user_id из JWT)
- INT-3 (WebSocket): JWT в query-параметре

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

- Экран результата эскиза: кнопка «Примерить» → открывает модальное окно с выбором манекена
- Модальное окно выбора манекена: сетка манекенов (рука, нога, спина, грудь, плечо, икра, запястье, шея), выбор + параметры (scale, rotation, opacity, offset_x, offset_y)
- Экран прогресса: job_id, прогресс-бар, статус обработки
- Экран результата: превью примерки (S3-ключ → presigned URL), кнопка «Скачать», кнопка «Поделиться»

### 4.2. Пользовательские сценарии

**Основной поток (FR-3):**
1. Пользователь открывает результат эскиза → нажимает «Примерить»
2. Выбирает манекен (body_part), настраивает параметры → INT-1
3. Получает job_id → переключается на экран прогресса
4. Подключается к WebSocket → получает прогресс в реальном времени
5. При `status=done` → INT-4 → показывает результат примерки

**Ветвление (polling fallback):**
1. WebSocket не подключился → polling каждые 5 секунд → INT-2
2. При `status=done` → INT-4 → показывает результат

**Ветвление (ошибка обработки):**
1. AI-обработка завершилась ошибкой → WS отправляет `type=error` или polling возвращает `status=failed`
2. Фронт показывает ошибку + кнопку «Повторить»

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `idle` | До отправки запроса | Форма выбора манекена и параметров |
| `submitting` | Отправка POST /v1/tryon | Спиннер «Отправка...» |
| `pending` | Job создан, обработка не началась | «Задача в очереди...» |
| `processing` | Job running, progress < 100 | Прогресс-бар с процентом |
| `done` | Job done, status=done | Превью примерки, кнопки «Скачать», «Поделиться» |
| `error` | Job failed, status=failed | Сообщение об ошибке + кнопка «Повторить» |
| `error_network` | WS disconnect + polling не отвечает | «Соединение потеряно» + кнопка «Повторить» |

### 4.3.1. Loading и таймауты

- **Таймаут отправки запроса:** 10 секунд
- **Таймаут polling:** 10 секунд
- **Polling интервал:** 5 секунд (если WS недоступен)
- **Hard-limit AI-обработки:** 120 секунд (согласно БТ)
- При таймауте → состояние `error_network` + кнопка «Повторить»

### 4.4. Доступ по ролям в UI

- `client`, `master`, `admin`: полный доступ к примерке

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- INT-1: синхронный ответ (202 Accepted), обработка асинхронная
- INT-2: синхронный запрос к PostgreSQL
- INT-3: WebSocket, Redis pub/sub
- AI-пайплайн (stub): ~5 секунд на MVP (в будущем — до 120 секунд для MediaPipe + warp)
- Очередь Celery: `gpu` (для try-on, т.к. требует больше ресурсов)
- Retry: max 3 попытки, exponential backoff (10s, 30s, 90s)

### 5.2. Надёжность/деградация

- При недоступности S3: API возвращает 503, фронт показывает «хранилище временно недоступен»
- При недоступности Redis: Celery не может забирать задачи
- При недоступности MongoDB: результат сохраняется в S3, но MongoDB не обновляется — ошибка логируется
- Job при `failed` с `retry_count < 3` автоматически перезапускается воркером

### 5.3. Безопасность/доступ (сводно)

- JWT-авторизация на всех эндпоинтах
- Валидация params: scale 0.1–5.0, rotation -180–180, opacity 0.0–1.0, offset -100–100
- S3-ключи иммутабельны
- Ownership-проверка на INT-1 (sketch ownership), INT-2, INT-4, INT-5

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. BE: миграции БД (нет), API-эндпоинты (INT-1, INT-2, INT-4, INT-5)
2. Workers: Celery-воркер с AIEngine.try_on() stub, очередь `gpu`
3. FE: интеграция с новыми эндпоинтами + WebSocket

BE и workers деплоятся одновременно, FE — после.

### 6.2. Обратная совместимость

- На данном этапе нет существующих потребителей — обратная совместимость не применима
- Все эндпоинты версионируются (`/v1/...`)

### 6.3. Фиче-флаги

Не применимо: задача не использует фиче-флаги

### 6.4. План отката

- **Откат только BE:** API перестаёт создавать jobs для try-on, старые jobs остаются в `pending`/`running`. FE на старой версии не вызывает новые эндпоинты — безопасно.
- **Откат только FE:** BE отдаёт новые эндпоинты, FE игнорирует — безопасно.
- **Откат workers:** jobs остаются `running` indefinitely — FE показывает прогресс-бар, но не получает финальный статус.

### 6.5. Преднастройка до релиза (чек-лист)

- [ ] Роли в security-сервисе — роли `client`, `master`, `admin` (из TB-02)
- [ ] DDL-миграция в репо владеющего сервиса — нет (таблицы из TB-03)
- [ ] Конфиги по окружениям (dev/staging/prod) — S3_URL, REDIS_URL, CELERY_BROKER_URL, AI_ENGINE=stub
- [ ] Сервисные аккаунты для межсервисных вызовов — не требуется
- [x] Фиче-флаги заведены — не требуются
