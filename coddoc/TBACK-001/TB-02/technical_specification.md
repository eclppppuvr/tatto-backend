## 1. Обзор изменения

### 1.1. Что делаем и тип изменения
**Суть:** Реализуем систему аутентификации и личный кабинет пользователя. Пользователь регистрируется по email и паролю, получает JWT-токены (access + refresh), входит в систему и получает доступ к личному кабинету с историей эскизов и настройками профиля.

**Тип:** новый функционал
**Стороны:** Fullstack

### 1.2. Затронутые сервисы и владельцы

| Сервис | Роль в задаче | Владелец/команда | Происхождение |
|--------|---------------|------------------|---------------|
| API (tatto-backend) | Новый сервис, владелец всех взаимодействий | Команда проекта | 🟢 |

### 1.3. Связь с бизнес-требованиями
Реализует FR-4 из БТ: пользователь регистрируется, входит в систему и получает доступ к личному кабинету с историей эскизов и настройками профиля.

## 2. Взаимодействия (ядро)

### INT-1. Регистрация пользователя — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** пользователь заполняет форму регистрации (email, пароль)
- **Контракт (запрос):** `POST /v1/auth/register`
  - `email` (string, required) — валидация по RFC 5322
  - `password` (string, required) — мин. 8 символов
- **Контракт (ответ):** `201 Created`
  - `id` (UUID) — ID пользователя
  - `email` (string)
  - `role` (enum: `client`, `master`, `admin`) — default `client`
  - `access_token` (string) — JWT access-токен
  - `refresh_token` (string) — JWT refresh-токен (или токен-хэш)
- **Пример запроса:**
  ```json
  {
    "email": "user@example.com",
    "password": "securePass123"
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "email": "user@example.com",
    "role": "client",
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refresh_token": "rt_a1b2c3d4e5f67890"
  }
  ```
- **Ошибки:**
  - `409 Conflict` — «Пользователь с таким email уже существует»
  - `422 Unprocessable` — «Валидация: email некорректен / пароль менее 8 символов»
- **Состояния UI по ответу:** значение → редирект в личный кабинет; ошибка → показать сообщение
- **Авторизация:** не требуется
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-2. Вход в систему (Login) — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** пользователь вводит email и пароль
- **Контракт (запрос):** `POST /v1/auth/login`
  - `email` (string, required)
  - `password` (string, required)
- **Контракт (ответ):** `200 OK`
  - `access_token` (string) — JWT access-токен
  - `refresh_token` (string)
  - `user` (object) — `id`, `email`, `role`
- **Пример запроса:**
  ```json
  {
    "email": "user@example.com",
    "password": "securePass123"
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refresh_token": "rt_a1b2c3d4e5f67890",
    "user": {
      "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
      "email": "user@example.com",
      "role": "client"
    }
  }
  ```
- **Ошибки:**
  - `401 Unauthorized` — «Неверный email или пароль»
  - `403 Forbidden` — «Аккаунт заблокирован»
- **Состояния UI по ответу:** значение → сохранение токенов, редирект; ошибка → показать сообщение
- **Авторизация:** не требуется
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-3. Обновление токена (Refresh) — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** access-токен истёк (401), фронт отправляет refresh-токен
- **Контракт (запрос):** `POST /v1/auth/refresh`
  - `refresh_token` (string, required)
- **Контракт (ответ):** `200 OK`
  - `access_token` (string) — новый access-токен
  - `refresh_token` (string) — новый refresh-токен (ротация)
- **Пример запроса:**
  ```json
  {
    "refresh_token": "rt_a1b2c3d4e5f67890"
  }
  ```
- **Пример ответа (успех):**
  ```json
  {
    "access_token": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...",
    "refresh_token": "rt_f6e5d4c3b2a10987"
  }
  ```
- **Ошибки:**
  - `401 Unauthorized` — «Refresh-токен недействителен или истёк»
  - `401 Unauthorized` — «Токен отозван»
- **Состояния UI по ответу:** значение → подмена токенов; ошибка → выход из системы, редирект на логин
- **Авторизация:** не требуется (проверка refresh-токена в БД)
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-4. Получение профиля пользователя — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** загрузка личного кабинета
- **Контракт (запрос):** `GET /v1/users/me`
  - Authorization: `Bearer <access_token>`
- **Контракт (ответ):** `200 OK`
  - `id` (UUID)
  - `email` (string)
  - `role` (enum: `client`, `master`, `admin`)
  - `is_active` (boolean)
  - `profile` (object | null) — `display_name`, `avatar_s3_key`, `bio`, `preferences`
  - `created_at` (ISO 8601)
- **Пример ответа (успех):**
  ```json
  {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "email": "user@example.com",
    "role": "client",
    "is_active": true,
    "profile": {
      "display_name": "Иван Петров",
      "avatar_s3_key": "avatars/a1b2c3d4.jpg",
      "bio": "Тату-мастер, 5 лет опыта",
      "preferences": {"theme": "dark", "language": "ru"}
    },
    "created_at": "2026-10-15T10:30:00Z"
  }
  ```
- **Ошибки:**
  - `401 Unauthorized` — «Токен недействителен»
  - `404 Not Found` — «Пользователь не найден»
- **Состояния UI по ответу:** значение → отображение профиля; ошибка → редирект на логин
- **Авторизация:** JWT required, любой valid user
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-5. Обновление профиля — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** пользователь сохраняет изменения профиля
- **Контракт (запрос):** `PUT /v1/users/me/profile`
  - Authorization: `Bearer <access_token>`
  - `display_name` (string, optional, max 100)

  - `preferences` (object, optional) — JSON
- **Контракт (ответ):** `200 OK` — обновлённый профиль (как в INT-4)
- **Пример запроса:**
  ```json
  {
    "display_name": "Иван Петров",
    "bio": "Тату-мастер, 5 лет опыта"
  }
  ```
- **Ошибки:**
  - `401 Unauthorized` — «Токен недействителен»
  - `422 Unprocessable` — «Валидация: display_name более 100 символов»
- **Состояния UI по ответу:** значение → обновлённый UI; ошибка → показать сообщение
- **Авторизация:** JWT required, только свой профиль
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-6. История эскизов пользователя — 🟢
- **Вид:** новое
- **Граница/направление:** FE → BE
- **Триггер:** пользователь открывает вкладку «История эскизов»
- **Контракт (запрос):** `GET /v1/users/me/sketches?page=1&limit=20`
  - Authorization: `Bearer <access_token>`
  - `page` (integer, optional, default 1)
  - `limit` (integer, optional, default 20, max 100)
- **Контракт (ответ):** `200 OK`
  - `items` (array) — список эскизов: `id`, `title`, `source`, `s3.thumbnail`, `created_at`
  - `total` (integer) — общее количество
  - `page` (integer)
  - `limit` (integer)
- **Пример ответа (успех):**
  ```json
  {
    "items": [
      {
        "id": "sk_a1b2c3d4",
        "title": "Моя тату",
        "source": "extract",
        "s3": { "thumbnail": "sketches/sk_a1b2c3d4_thumb.jpg" },
        "created_at": "2026-10-20T14:00:00Z"
      }
    ],
    "total": 45,
    "page": 1,
    "limit": 20
  }
  ```
- **Ошибки:**
  - `401 Unauthorized` — «Токен недействителен»
  - `422 Unprocessable` — «page < 1 или limit > 100»
- **Состояния UI по ответу:** значение → список эскизов; пусто → «У вас пока нет эскизов»; ошибка → показать сообщение
- **Авторизация:** JWT required
- **Происхождение:** 🟢 новое
- **Трассировка:** FR-4

### INT-7. Выход из системы (Logout) — 🟢

## 3. Backend — ответственность

### 3.1. По сервисам

**API (tatto-backend)** — реализует все INT-1..INT-7.

- INT-1 (register): хеширование пароля (bcrypt), создание пользователя, генерация JWT, сохранение refresh-токена
- INT-2 (login): верификация пароля, генерация JWT, сохранение refresh-токена
- INT-3 (refresh): валидация refresh-токена в БД, ротация токенов
- INT-4 (get profile): чтение пользователя + профиля из PostgreSQL
- INT-5 (update profile): обновление профиля в PostgreSQL
- INT-6 (sketches history): чтение эскизов из MongoDB (или PostgreSQL), пагинация
- INT-7 (logout): отзыв refresh-токена из БД

### 3.2. Данные и хранение

- 🟢 `users` — таблица PostgreSQL: `id` (UUID, PK), `email` (VARCHAR 255, UNIQUE, NOT NULL), `hashed_password` (VARCHAR 255, NOT NULL), `role` (ENUM: client, master, admin, default client), `is_active` (BOOLEAN, default true), `created_at` (TIMESTAMPTZ), `updated_at` (TIMESTAMPTZ)
- 🟢 `profiles` — таблица PostgreSQL: `user_id` (UUID, PK, FK → users.id), `display_name` (VARCHAR 100), `avatar_s3_key` (TEXT), `bio` (TEXT), `preferences` (JSONB)
- 🟢 `refresh_tokens` — таблица PostgreSQL: `id` (UUID, PK), `user_id` (UUID, FK → users.id ON DELETE CASCADE), `token_hash` (VARCHAR 255, UNIQUE), `expires_at` (TIMESTAMPTZ), `revoked` (BOOLEAN, default false), `created_at` (TIMESTAMPTZ)
- Индексы: `(email UNIQUE)`, `(user_id, created_at DESC)` для profiles, `(token_hash UNIQUE)` для refresh_tokens
- Миграции: 3 DDL-миграции (users, profiles, refresh_tokens) — точный синтаксис финализирует владеющий сервис

### 3.3. Авторизация/доступ на бэке

- Все эндпоинты кроме INT-1, INT-2, INT-3 требуют JWT в заголовке `Authorization: Bearer <token>`
- Валидация: проверка подписи JWT, срока действия
- INT-4, INT-5, INT-6: пользователь видит только свои данные (user_id из JWT)
- INT-5: пользователь может обновить только свой профиль
- Роли: admin может управлять пользователями (выходит за рамки MVP TB-02, но инфраструктура готова)

## 4. Frontend — ответственность

### 4.1. Где и что меняется в UI

- Экран регистрации: форма (email, пароль, подтверждение пароля), кнопка «Зарегистрироваться»
- Экран входа: форма (email, пароль), кнопка «Войти», ссылка «Забыли пароль?»
- Личный кабинет:
  - Вкладка «Профиль»: отображение и редактирование display_name, bio, avatar
  - Вкладка «История эскизов»: пагинированный список эскизов (INT-6)
- Кнопка «Выйти» в шапке

### 4.2. Пользовательские сценарии

**Основной поток (FR-4):**
1. Пользователь открывает сайт → редирект на логин
2. Вводит email и пароль → INT-2 → получает токены
3. Сохраняет токены в localStorage / httpOnly cookie
4. Переходит в личный кабинет → INT-4 (профиль) + INT-6 (история)
5. Редактирует профиль → INT-5
6. Нажимает «Выйти» → INT-7

**Ветвление (регистрация):**
1. Пользователь нажимает «Зарегистрироваться» → INT-1
2. Получает токены → редирект в личный кабинет

**Ветвление (ротация токена):**
1. Access-токен истёк → API возвращает 401
2. Фронт отправляет refresh-токен → INT-3
3. Получает новые токены → повторяет исходный запрос

### 4.3. Состояния (именованные)

| Имя состояния | Условие | Что видит пользователь |
|---------------|---------|------------------------|
| `loading` | первый запрос / после инвалидации | Спиннер / скелетон |
| `value` | 2xx, значение ≠ null | Отображение данных |
| `empty` | 2xx, null / пустой список | «Нет данных» / «У вас пока нет эскизов» |
| `error_network` | 5xx / таймаут / сеть | «Сервис временно недоступен» + кнопка «Повторить» |
| `error_forbidden` | 403 | «Доступ запрещён» |
| `error_unauthorized` | 401, refresh не помог | Редирект на логин |

### 4.3.1. Loading и таймауты

- **Таймаут cold-path** (первый запрос): 10 секунд
- **Таймаут warm-path** (последующие): 5 секунд
- **Polling:** нет (данные запрашиваются по действию пользователя)
- При таймауте / 5xx → состояние `error_network` + кнопка «Повторить»

### 4.4. Доступ по ролям в UI

- `client`: профиль, история эскизов
- `master`: профиль, история эскизов + (в будущем) демонстрация клиентам
- `admin`: управление пользователями (выходит за рамки MVP TB-02)

## 5. Нефункциональные требования

### 5.1. Синхронность, кэш, производительность

- Все взаимодействия — синхронный HTTP/JSON
- JWT access-токен: TTL 15 минут
- JWT refresh-токен: TTL 7 дней
- Refresh-токен ротация: при каждом использовании старый токен аннулируется
- Пароль хеширование: bcrypt, cost factor 12
- Ожидаемая нагрузка (MVP): до 1000 пользователей, до 100 активных сессий

### 5.2. Надёжность/деградация

- При недоступности PostgreSQL: API возвращает 503, фронт показывает «сервис недоступен»
- При истечении refresh-токена: фронт принудительно выходит из системы (401)
- Интегрированная защита от brute-force: после 5 неудачных попыток входа — блокировка на 15 минут (rate-limit по IP)

### 5.3. Безопасность/доступ (сводно)

- Пароли хешируются bcrypt (никогда не хранятся в открытом виде)
- JWT подписывается HMAC-SHA256 с секретным ключом (через переменную окружения)
- Refresh-токены хранятся как хэш (SHA-256) в БД, не в открытом виде
- CSRF-защита: httpOnly + Secure cookie для refresh-токена (если фронт — SPA)
- CORS: настройка разрешённых origin'ов через переменную окружения

## 6. Релиз и интеграция

### 6.1. Порядок выката

1. BE: миграции БД + API-эндпоинты
2. FE: интеграция с новыми эндпоинтами

BE деплоится первым, так как FE ожидает наличие эндпоинтов.

### 6.2. Обратная совместимость

- На данном этапе нет существующих потребителей — обратная совместимость не применима
- В будущем: все эндпоинты версионируются (`/v1/...`)

### 6.3. Фиче-флаги

Не применимо: задача не использует фиче-флаги

### 6.4. План отката

- **Откат только BE:** DB-миграции откатываются (down-миграция). FE на старой версии не вызывает новые эндпоинты — безопасно.
- **Откат только FE:** BE отдаёт новые эндпоинты, FE игнорирует — безопасно.

### 6.5. Преднастройка до релиза (чек-лист)

- [x] Роли в security-сервисе — роли `client`, `master`, `admin` встроены в БД (users.role)
- [ ] DDL-миграция в репо владеющего сервиса — 3 миграции: users, profiles, refresh_tokens
- [ ] Конфиги по окружениям (dev/staging/prod) — JWT_SECRET, DB_URL, S3_URL
- [ ] Сервисные аккаунты для межсервисных вызовов — не требуется (MVP, один сервис)
- [x] Фиче-флаги заведены — не требуются
